# 인증 — 개인 API 토큰

스크립트·CI·외부 시스템에서 플랫폼 API를 호출하려면 **개인 API 토큰**을 쓴다. 브라우저 로그인(Keycloak)과는 별개로, 사람이 아닌 클라이언트를 위한 인증 수단이다. 이 문서는 토큰의 발급·사용·폐기와 토큰 관련 오류를 다룬다.

## 무엇인가

아틀라시안의 API 토큰과 같은 개념이다. 로그인한 사용자가 자기 계정에 묶인 토큰을 발급하고, 클라이언트는 그 토큰을 요청 헤더에 실어 보낸다. 토큰으로 호출하면 **토큰 주인의 권한을 넘지 않는 범위**에서 동작한다 — 내가 볼 수 있는 위키 스페이스와 ALM 프로젝트를 토큰도 볼 수 있고, 내가 못 하는 일은 토큰도 못 한다. 여기에 더해 발급할 때 고른 **스코프**만큼만 쓸 수 있다(아래 [스코프](#스코프) 참고). 스코프는 권한을 늘리지 않고 줄이기만 한다.

## 발급하기

1. 로그인한 뒤 **`/app/tokens`** (앱 셸 왼쪽 메뉴의 "API 토큰")로 간다.
2. **새 토큰**을 누르고 **라벨**(용도를 알아볼 수 있는 이름, 1~100자)과 **만료일**(30/90/180/365일 중 선택, 기본 90일)을 정한다.
3. **권한(스코프)**을 고른다. 제품(WIKI·ALM·조직)마다 읽기/쓰기를 체크하고, 관리 API가 필요하면 "관리자 API"를 함께 켠다. 기본값은 읽기 세 개(`wiki:read` `alm:read` `org:read`)이며 하나도 고르지 않으면 발급할 수 없다.
4. 발급 직후 토큰 전문이 **한 번만** 표시된다. 복사해서 안전한 곳(비밀 저장소·환경변수)에 보관한다. 창을 닫으면 다시 볼 수 없고, 잃어버리면 폐기하고 새로 발급해야 한다.

목록 화면에서는 토큰을 `chanho_pat_…ab12`처럼 뒤 4자만으로 식별하며, 라벨·만든 날·만료일·마지막 사용 시각·권한(스코프)·상태(활성 · 곧 만료(7일 이내) · 만료 · 폐기)를 보여 준다.

스코프는 발급 뒤에 바꿀 수 없다. 범위를 넓히거나 좁히려면 새 토큰을 발급하고 옛 토큰을 폐기한다.

한도와 만료:

| 항목 | 값 |
|---|---|
| 사용자당 활성 토큰 | 최대 25개 |
| 만료 기간 | 1~365일 (기본 90일) |
| 무기한 토큰 | 없음 — 만료일은 필수 |

## 사용하기

토큰은 `Authorization` 헤더에 Bearer 방식으로 싣는다. 토큰은 `chanho_pat_`로 시작한다.

```
Authorization: Bearer chanho_pat_…
```

아래 예시의 `https://<your-host>`는 플랫폼이 배포된 호스트로 바꾼다. 경로는 브라우저에서 쓰는 API와 동일하다.

내 계정 정보 확인:

```bash
curl -H "Authorization: Bearer chanho_pat_…" \
  https://<your-host>/api/me
```

내가 볼 수 있는 위키 스페이스 목록:

```bash
curl -H "Authorization: Bearer chanho_pat_…" \
  https://<your-host>/api/wiki/spaces
```

내가 볼 수 있는 ALM 프로젝트 목록:

```bash
curl -H "Authorization: Bearer chanho_pat_…" \
  https://<your-host>/api/alm/projects
```

`/api/wiki/**`, `/api/alm/**`, `/api/org/**`, `/api/me`에 같은 방식으로 쓸 수 있다. 어떤 경로가 열리는지는 토큰의 [스코프](#스코프)가 정한다.

## 스코프

토큰은 발급할 때 고른 스코프 안에서만 동작한다. 스코프는 일곱 개다.

| 스코프 | 허용 경로 | 메서드 |
|---|---|---|
| `wiki:read` | `/api/wiki/**` | `GET` · `HEAD` · `OPTIONS` |
| `wiki:write` | `/api/wiki/**` | 전부 (읽기 포함) |
| `alm:read` | `/api/alm/**` | `GET` · `HEAD` · `OPTIONS` |
| `alm:write` | `/api/alm/**` | 전부 (읽기 포함) |
| `org:read` | `/api/org/**` | `GET` · `HEAD` · `OPTIONS` |
| `org:write` | `/api/org/**` | 전부 (읽기 포함) |
| `admin` | `/api/wiki/admin/**` · `/api/alm/admin/**` · `/api/org/admin/**` · `/api/migration/**` · `/api/agent/**` | 해당 경로에 **추가로** 필요 |

규칙 셋만 기억하면 된다.

- **`*:write`는 같은 제품의 `read`를 포함한다.** `wiki:write`가 있으면 위키 GET도 통과한다. 발급 화면에서 쓰기를 켜면 읽기가 자동으로 켜지고 잠기는 이유다.
- **`admin`은 제품 스코프를 대신하지 않는다.** 관리 API는 둘 다 필요하다 — 예를 들어 `GET /api/wiki/admin/stats`는 `wiki:read`와 `admin`을 함께 요구한다. 물론 `admin` 스코프가 있어도 계정 자체가 전역 관리자가 아니면 서비스가 `403`으로 막는다. 스코프는 권한을 주지 않는다.
- **표에 없는 경로는 토큰으로 부를 수 없다.** `/api/board/**`, `/api/auth/**`, 관리자 대시보드용 `/api/platform/**`은 브라우저 로그인 세션 전용이다. 예외는 `/api/me` 하나로, 스코프와 무관하게 항상 통과한다.

스코프가 모자라면 `403`이 온다.

```http
HTTP/1.1 403 Forbidden
Content-Type: application/json

{ "error": "insufficient_scope" }
```

```bash
# wiki:read 만 가진 토큰으로 페이지를 만들려는 경우
curl -i -X POST -H "Authorization: Bearer chanho_pat_…"   -H "Content-Type: application/json"   -d '{"spaceId":1,"title":"새 페이지"}'   https://<your-host>/api/wiki/pages
# → HTTP/1.1 403 Forbidden
# → {"error":"insufficient_scope"}
```

재시도해도 풀리지 않는다. 필요한 스코프로 새 토큰을 발급해야 한다.

스코프가 도입되기 전에 만든 토큰은 제한 없이 통과한다(목록에 권한이 "전체"로 표시된다). 쓰던 자동화를 최소 권한으로 바꾸려면 필요한 스코프만 고른 토큰을 새로 발급하고 옛 토큰을 폐기한다.

## 동작 원리

토큰은 게이트웨이에서 처리된다.

1. 게이트웨이가 `Authorization: Bearer chanho_pat_…` 요청을 받으면 인증 서버에 토큰을 확인하고, **짧은 수명(5분)의 플랫폼 JWT**로 바꾼다.
2. 게이트웨이가 요청 경로·메서드를 토큰의 스코프(교환된 JWT의 `scope` 클레임)와 대조한다. 모자라면 여기서 `403 insufficient_scope`로 끊고 뒤쪽 서비스로 보내지 않는다.
3. 통과한 요청은 바뀐 JWT가 원래의 `Authorization` 헤더 자리에 들어가 뒤쪽 서비스(wiki·alm·org·board…)로 전달된다. 서비스는 토큰의 존재를 모르고 **JWT만 본다** — 브라우저 세션으로 호출할 때와 같은 경로다. 스코프 검사는 게이트웨이에서만 일어난다.
4. 게이트웨이는 확인 결과를 **60초** 동안 캐시한다. 그래서 토큰을 폐기해도 이미 캐시된 결과가 남아 있는 **최대 60초** 동안은 요청이 통과할 수 있고, 그 뒤에는 차단된다.
5. 토큰이 아닌 일반 JWT나 `Authorization` 헤더가 없는 요청은 이 과정을 거치지 않고 그대로 지나간다.

토큰 원문은 서버에 저장되지 않는다. 인증 서버는 해시만 보관하고, 원문은 발급 응답에 한 번 실릴 뿐이다.

## 오류 응답

토큰 관련 오류는 JSON 본문 `{"error": "<코드>"}`로 온다. 서비스 API의 오류 본문도 같은 모양이지만 `error`에 사람이 읽는 메시지가 들어간다는 점이 다르다([오류 처리](./30-errors.md) 참고).

| HTTP | `error` | 뜻 |
|---|---|---|
| 401 | `invalid_token` | 토큰이 없거나(알 수 없는 값), 만료됐거나, 폐기됐다. 세 경우를 구분하지 않고 같은 응답을 준다. |
| 503 | `auth_unavailable` | 게이트웨이가 인증 서버에 토큰을 확인하지 못했다(인증 서버 장애·타임아웃). 잠시 뒤 다시 시도한다. |
| 403 | `insufficient_scope` | 토큰의 스코프로는 그 경로·메서드를 부를 수 없다([스코프](#스코프) 참고). 필요한 스코프로 새 토큰을 발급한다. |
| 403 | `pat_cannot_manage_tokens` | 토큰으로 토큰 관리 API(`/api/auth/tokens`)나 에이전트 생성 API(`/api/auth/agents`)를 호출했다. 두 경로 모두 브라우저 로그인 세션으로만 할 수 있다 — 토큰이 새 토큰을 낳는 것을 막기 위해서다. 관리자 계정의 토큰이라도 마찬가지다. |
| 409 | `token_limit` | 활성 토큰이 이미 25개라 새로 발급할 수 없다. 안 쓰는 토큰을 폐기한 뒤 다시 발급한다. |
| 400 | `label_required` / `invalid_expiry` | 발급 요청의 라벨이 비었거나(1~100자), 만료 일수가 1~365 범위를 벗어났다. |
| 400 | `scopes_required` / `scopes_invalid` | 발급 요청에 스코프가 하나도 없거나, 표에 없는 값이 섞였다. |
| 404 | `not_found` | 폐기하려는 토큰이 없거나 내 것이 아니다. 남의 토큰은 존재 여부를 알려 주지 않는다. |

401이 반복되면 토큰 값이 정확히 복사됐는지(앞뒤 공백·줄바꿈), 만료되지 않았는지, `/app/tokens`에서 폐기되지 않았는지 순서로 확인한다.

## 폐기와 교체

- `/app/tokens` 목록에서 토큰을 **폐기**하면 그 순간부터 새 요청은 거부된다. 다만 게이트웨이 캐시 때문에 폐기 직전에 확인된 요청은 **최대 60초**까지 통과할 수 있다.
- 폐기는 되돌릴 수 없다. 같은 용도가 계속 필요하면 새 토큰을 발급해 클라이언트 설정을 바꾼다.
- 토큰이 코드·로그·채팅 등에 노출됐다고 의심되면 **즉시 폐기**하고 재발급한다. 노출 여부를 확인하느라 미루지 않는다.
- 만료된 토큰은 자동으로 거부되며, 목록에는 "만료" 상태로 남는다. 새 토큰을 발급해 교체한다.

## 보안 권고

- **비밀 저장소·환경변수에 둔다.** CI의 secret, 비밀 관리 도구, 로컬 `.env`처럼 저장소에 올라가지 않는 곳에 보관하고 코드에서는 환경변수로 읽는다.
- **코드·로그에 남기지 않는다.** 소스에 하드코딩하거나 요청 로그·에러 메시지에 헤더를 통째로 찍지 않는다.
- **만료를 짧게 잡는다.** 필요한 기간만큼만 발급한다. 오래 쓰는 자동화라도 주기적으로 재발급하는 편이 안전하다.
- **자동화마다 토큰을 분리한다.** CI, 개인 스크립트, 외부 연동에 같은 토큰을 돌려쓰지 않는다. 하나가 유출돼도 그것만 폐기하면 된다.
- **라벨로 용도를 적는다.** "ci-deploy", "노트북 백업 스크립트"처럼 어디서 쓰는지 알 수 있게 붙여 두면 폐기·교체 때 헷갈리지 않는다.

## 한계

현재 제공하지 않는 것:

- **발급 뒤 스코프 변경** — 범위를 바꾸려면 새로 발급한다.
- **경로·리소스 단위 제한** — 스코프는 제품(위키·ALM·조직) 단위다. "이 스페이스만" 같은 제한은 없다.
- **조직 관리 토큰** — 개인 계정 토큰만 있다.
- **Basic 인증**(`이메일:토큰`) — `Authorization: Bearer`만 지원한다.
- **토큰별 rate-limit** — 토큰 요청은 클라이언트 IP 단위로 제한된다([요청 제한](./70-rate-limits.md) 참고).

각 서비스 API의 엔드포인트·요청·응답은 [API 레퍼런스](../api-reference/wiki/README.md)에 정리돼 있다.
